# Prompt - Seccion Base de Datos

Lee CLAUDE.md primero, todo lo de ahi aplica. Este prompt es para dejar el
schema completo y correcto en un solo paso, no una tabla a la vez.

## Tarea

Generar el `schema.prisma` completo para las 5 areas del sistema, mas las
migraciones SQL crudas necesarias para lo que Prisma no cubre nativamente
(constraint EXCLUDE, politicas RLS, extension btree_gist). No dejar ninguna
tabla "para despues", generar las 5 areas en esta misma pasada.

### 1. Nucleo (usuarios, roles, RLS)
- `usuarios`: id, email, password_hash, rol (enum: ADMIN, PROFESIONAL,
  PRACTICANTE), activo, fecha_expiracion_acceso (nullable, solo aplica a
  PRACTICANTE), timestamps.
- `historial_accesos_practicante` (antes `accesos_temporales`, movida al
  Nucleo en 01d): bitacora append-only de otorgamiento/revocacion/expiracion
  de acceso a practicantes (quien, cuando, por quien). Se escribe solo via
  funciones SECURITY DEFINER, junto con el cambio en `usuarios`.
- Migracion cruda: `CREATE EXTENSION IF NOT EXISTS btree_gist;`
- Migracion cruda: politicas RLS sobre `pacientes` y `fichas_clinicas`
  (ver abajo) usando `current_setting('app.current_usuario_id', true)` y
  `current_setting('app.current_rol', true)`. Documentar en un comentario SQL
  que estas variables se setean por request via `SET LOCAL` antes de cada
  transaccion Prisma (eso lo hace el prompt de APIs, aqui solo dejar la
  politica lista).

### 2. Fichas y Pacientes
- `pacientes`: datos basicos + `fecha_nacimiento` + `profesional_id` (FK,
  RESTRICT en delete, nunca CASCADE).
- `adultos_responsables`: paciente_id (FK), nombre, contacto. Un paciente
  puede tener mas de uno.
- `fichas_clinicas`: 1:1 con paciente, no se borra nunca.
- `evoluciones`: FK a ficha_clinica, append-only (sin campo de update real,
  cualquier correccion es una fila nueva referenciando a la anterior), autor
  (profesional_id), timestamp.
- `derivaciones`: ficha_clinica_id, profesional_origen_id,
  profesional_destino_id, motivo, fecha, activa (bool). Mientras `activa`,
  la politica RLS debe permitir lectura al profesional_destino tambien.
- Politica RLS en `pacientes` y `fichas_clinicas`: permitir fila si
  `profesional_id = current_setting(...)` O rol = ADMIN Y la columna
  consultada no es contenido clinico (para ADMIN, la politica debe cubrir
  agenda/metadata, no el contenido de `evoluciones`: en `evoluciones` la
  politica NO debe tener excepcion para ADMIN salvo derivacion activa).

### 3. Agenda y Espacios
- `espacios`: nombre/numero de box, activo.
- `citas`: espacio_id, profesional_id, paciente_id, rango horario
  (`tsrange` o dos columnas timestamp), estado (enum: CONFIRMADA, CANCELADA).
- Migracion cruda: `ALTER TABLE citas ADD CONSTRAINT no_solapamiento
  EXCLUDE USING gist (espacio_id WITH =, rango_horario WITH &&) WHERE
  (estado = 'CONFIRMADA');` (ajustar sintaxis exacta al tipo de columna
  elegido). Repetir logica equivalente para que un profesional tampoco tenga
  dos citas confirmadas que se solapen.
- `bloqueos_temporales`: espacio_id, usuario_id, expira_en. Sin relacion con
  el constraint anterior, es solo la capa de UX del soft-lock.
- Validacion de menor de edad: no es un constraint de DB por si solo (la
  edad es calculada), dejar un CHECK o trigger que impida insertar una cita
  para un paciente menor de 18 (calculado desde `pacientes.fecha_nacimiento`)
  si no existe fila en `adultos_responsables` para ese paciente. Documentar
  si se implementa como trigger o se deja para la capa de servicio, y por que.

### 4. Equipo (RR.HH. y Perfiles)
- Extiende `usuarios` con `profesionales` (especialidad, enfoque terapeutico,
  tarifa, modalidad) y `practicantes` (fecha_inicio, fecha_termino_practica).
- (La bitacora de accesos de practicantes vive en el Nucleo, ver seccion 1.)

### 5. Cobros
- `arriendos`: profesional_id, monto, porcentaje_comision.
- `pagos`: cita_id (FK, nunca nullable, una boleta siempre cuelga de una
  cita real), monto, medio_pago, fecha.
- `boletas`: pago_id, numero, pdf_url o campo para generarlo.

## Restricciones que no se pueden dejar pendientes
- Ninguna tabla con datos clinicos permite DELETE real (usar `deleted_at`
  si hace falta soft-delete, nunca borrar la fila).
- Todo FK hacia `pacientes` o `fichas_clinicas` es RESTRICT, no CASCADE.
- El constraint EXCLUDE y las politicas RLS se entregan en esta misma
  pasada, no en un prompt futuro.

## Salida esperada
- `schema.prisma` completo.
- Carpeta de migraciones con el SQL crudo embebido donde Prisma no alcanza.
- Un archivo `seed.ts` minimo que cree un usuario ADMIN y dos PROFESIONAL de
  prueba, para poder probar la RLS manualmente apenas migre.
